我的个人项目里，大部分提交只有我一个人看。按理说"改了点东西"这样的提交信息也没人管，但半年后回头查一处改动为什么发生，看到的就是自己当初随手打的字。所以我给自己定了一套规范，不复杂，但严格执行。

## 标题行的三条规矩

提交信息的第一行是最重要的，因为 `git log --oneline` 只会显示它。

- **一行写完，不超过 50 个字符**。终端不会折行，超出的部分会被截断。
- **用动词开头，说清楚做了什么**。中文用"修复/新增/重构/删除"，英文用 `fix/add/refactor/remove`。
- **不写"更新了文件"这类无信息量的话**。信息量为零的提交，等于没写。

对比一下这两条：

```
# 差
update code

# 好
fix: 修正分页在最后一页多出一页的问题
```

第二条在半年后依然能被搜索到，第一条不能。

## 类型前缀

我用的是 Conventional Commits 的简化版，只保留自己真正常用的几类：

| 前缀 | 含义 | 什么时候用 |
| --- | --- | --- |
| `feat` | 新功能 | 增加了用户能感知的能力 |
| `fix` | 修 bug | 修正了错误行为 |
| `refactor` | 重构 | 行为不变，结构变了 |
| `docs` | 文档 | 只改注释、README |
| `chore` | 杂务 | 依赖升级、配置调整 |
| `style` | 格式 | 只动空格、换行，不动逻辑 |

> [!TIP]
> 判断 `refactor` 还是 `fix` 有一个简单的办法：**改完之后站点/程序的行为有没有变化？** 有变化就是 feat 或 fix，没变化就是 refactor。这个判断只需要三秒，但能让历史记录干净很多。

## 正文写什么

标题行之外的内容不是必须的，但有两种情况我一定会写正文：

第一，**这个改动有取舍**。为什么选 A 不选 B，当时考虑过什么方案。这类内容写在提交里比写在注释里合适，因为注释会随代码飘走，提交记录不会。

第二，**这个改动有副作用**。比如"删掉了旧的缓存逻辑，首次访问会慢 200ms"，这种信息必须留下，否则下次性能问题又要重新调查一遍。

```bash
git commit -m "refactor: 用构建时索引替换运行时搜索

搜索原先在浏览器里遍历全文，文章超过 30 篇后首次搜索要 1.2 秒。
改为构建时生成 JSON 索引，前端只做匹配，首次搜索降到 80ms。

副作用：索引文件约 40KB，随站点一起发布。"
```

多行提交信息在命令行里用一个 `-m` 加换行是可行的，但我更常在编辑器里写——`git commit` 不带参数会打开编辑器，反而更快。

## 关于提交粒度

我给自己定的标准是：**一个提交只做一件事，且能独立回滚**。

以前我经常攒一天的改动一次性提交，信息写成"这周的活儿"。后来有一次线上出问题，需要回滚其中一小部分，才发现根本拆不开。从那之后我改成完成一个小目标就提交一次，哪怕只是修好一个错别字。

> [!NOTE]
> 提交频率高不等于历史混乱。混乱来自"一个提交里塞了五件事"，而不是提交次数多。粒度小、信息准的历史，用 `git log -S` 搜关键词时几乎是万能的。

## 最后

这套规范最实际的好处，不是让代码更好看，而是让**未来的调查变便宜**。当我想知道某个样式为什么这么写、某个依赖为什么锁在那个版本，`git log` 能直接给出答案，而不是让我对着一堆 `update` 发呆。

一个人写代码，唯一的评审者就是时间。提交信息是写给时间看的。
